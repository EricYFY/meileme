# 核心循环实时化重构方案（回合制 → 实时经营）

## 一、背景与目标

当前玩法是**回合制**：游戏日开始时时钟暂停进入「决策窗口」，玩家必须守在电脑前配置好并点【开始今日仿真】，跑完（现实 1 小时 × 倍速）后才自动弹日报，然后进入下一天。

这带来两个问题：一是**节奏太慢**（1x 下一天要现实 1 小时，4x 也要 15 分钟）；二是**决策窗口要求玩家在线等待**，与「挂机经营」的定位冲突。

本次改为**实时经营**：仿真连续运行、玩家随时可下指令、指令次日 0 点生效、报告改为按需自选区间生成。

> ⚠️ 本次会**删除原「仿真运行期间玩家零干预」的硬约束**（用户明确要求）。改完后玩家随时可操作。

## 二、已确认的决策（不再变更）

| 项 | 决策 |
| :--- | :--- |
| 时间比例 | **现实 1 分钟 = 游戏 1 天**（`VIRTUAL_MS_PER_REAL_SECOND = 1440000`，1 现实秒 = 24 游戏分钟） |
| 倍速档位 | `0.5 / 1 / 2 / 4 / 8 / 16x`（16x = 3.75 秒/天） |
| 决策窗口 | **彻底取消**，无暂停时钟、无提交动作、无现实 5 分钟超时；连续运行 |
| 指令生效 | **次日 0 点生效**；建造费/地块解锁费**点击即扣**，其余（招聘/解雇/定价/广告/接单）只入队、费用按原规则日结体现 |
| 每日报告 | **不再自动弹**；每日结算照常执行（资金/口碑/季节/破产都需要），改为前端「📊 生成报告」自选 **1 / 7 / 30 / 365 天** 区间 |
| 换日感知 | 不弹窗，只在右侧**事件日志追加一行**（`第 N 天结算 · 净利润 ¥X · 资金 ¥Y`） |
| 历史数据 | 日结存一条汇总快照，**内存保留最近 365 天**，超出裁掉最旧 |
| 团建单 | 每天 0 点仍生成 0~2 单；**当天有效**，不操作 → 次日 0 点自动拒绝（无罚款）；接受 → **次日生效**，生效日结算时判定，不满足扣原罚款 |
| 指令撤销 | **不支持**；同类指令后入覆盖前入 |
| 时钟读数 | 顶部只显示**游戏时刻 HH:MM + 当日进度条**，不显示剩余倒计时 |
| 破产判定 | 保留：日结后资金 ≤ 0 → 广播破产并结束本局 |
| 季节 | 保留：每 30 游戏天切换 |

新增方法：

- **`scheduledLoop()` 保持 `@Scheduled(fixedRate = 1000)` 只负责推进时钟 + 跨日**（时钟推进量依赖执行间隔，**绝不可把它的频率改成 200ms**，否则会快 5 倍）。时钟广播改由上面新增的 200ms 方法专职负责。
- 换日序列（顺序即正确性）：
```
endDay(D)：settleDueTeamOrders(D) 判定今日生效单 → computeDailyReport(D) → 资金/口碑/天数

        → applyPendingCommands() 应用 D 天排队指令（接受的团建单置 ACCEPTED、effectiveDay=D+1）
        → day = D+1 → beginDay()
```
- 操作分派：`buildBuilding` / `unlockPlot` → 立即扣费 + 入队；`hireStaff` / `fireStaff` / `setRoomPrice` / `setAdBudget` / `acceptTeamOrder` → 只入队；统一广播 `RESORT_STATE`（带上 `pendingCommands`，前端即可显示「已排队 N 条」）

## 四、三块新设计要点

**1. 待生效指令队列** — 放 `Resort.pendingCommands`，随 `RESORT_STATE` 全量下发即得「已排队 N 条」，不新增消息类型。FIFO 应用，同类后入覆盖。与团建单协同的关键：`ACCEPT_TEAM_ORDER` 入队时**不改**订单状态，次日 0 点 `applyPendingCommands()` 才置 `ACCEPTED` 并设 `effectiveDay = day+1`；因此 `rejectStaleTeamOrders()` 必须排在 `applyPendingCommands()` **之后**，否则当天刚接的单会被当作未决单误清。

**2. 历史快照 + 区间报告** — `ResortRepository.history` 内存 List，超 365 裁最旧。聚合指标：区间与实际样本天数、收入 4 项合计与总额、支出 5 项合计、净利润、起止资金、起止口碑与变化、平均入住率、接待/溢出总数、团建满足/违约计数与收入/罚款、事件按类型计数、每日精简序列（日/季节/净利/入住率/接待/资金）、最好与最差日。命令 `REQUEST_RANGE_REPORT`，消息 `RANGE_REPORT`（只回请求方）；破产后仍允许查看。

**3. DayPhase 简化** — 只留 `RUNNING / GAME_OVER`；破产 = `GAME_OVER` + `gameOver=true` + `endReason`；暂停仍由 `paused` 布尔表达（时钟冻结、`virtualMsPerRealSecond = 0`）。`beginDay()` 仍广播 `DAY_STARTED` / `TEAM_ORDERS_OFFERED` / `RESORT_STATE` / `TIME_TICK`，只是不再进入任何等待态。

## 六、我锁定的假设（如与预期不符请指出）

1. 招人/解雇不即时扣钱（工资仍在日结扣），但**次日 0 点才上岗/离岗**（地图上员工次日出现/消失）。
2. 「结束并重置」会**清空历史**（新一局从零开始）。
3. 团建单结算完毕即从卡片区移出，结果只在事件日志与区间报告里体现。
4. 应用指令时**不再做余额校验**（钱在点击时已扣或本就不扣），不会因中途支出导致指令失败。

## 七、验证清单

1. **离线数值自检**：`1440000 × 60 == 86400000`；1x = 60 秒/天、4x = 15 秒、16x = 3.75 秒。
2. **编译/构建**：Java 用 `javac`（本机无 Maven，classpath 由 `~/.m2/repository` 的 jar 拼装，需排除 `*-sources.jar`/`*-javadoc.jar`）；前端 `npm run build`。
3. **三端重启实测**：开局即进入 RUNNING 且**没有**「开始今日仿真」；1x 下 60 秒换日、进度条连续、约 200ms 一条 `TIME_TICK`。
4. **指令生效**：建造/解锁点击即扣款并入队；招聘/定价/广告只入队；右侧显示「已排队 N 条」；跨日后第 2 天 `RESORT_STATE` 已生效（建筑出现、房价已变）。
5. **团建单**：当日接单 → 次日日结出结果（事件日志可见）；不接 → 次日自动拒绝且资金无罚款；容量不足 → 扣原罚款。
6. **报告**：1/7/30/365 各生成一次；样本不足时显示实际天数；破产画面仍可看。
7. **历史裁剪**：16x 连跑 366 天（约 23 分钟），`history` 长度恒为 365。
8. **刷新页面**：`RESORT_STATE` 带 `pendingCommands` / `scheduledOrders`，`TIME_TICK` 恢复走字。
9. **Python**：16x 下 NPC 不瞬移、换日后数秒内数量对齐、暂停时静止。

## 八、已知取舍

- 游戏时刻 HH:MM 在 1x 下每现实秒前进 24 游戏分钟，**数字会跳得很快**（这是所选时间比例的必然结果）；进度条会平滑推进。
- 报告「过去 1 年」需要先跑满 365 天；4x 约 1.5 小时、16x 约 23 分钟。
- 团建单在 4x 以上只有数秒阅读时间，可能来不及接——这是「当天有效」决策的必然结果。
- 历史只在内存，Java 重启即丢（重启本来就丢整局，不额外处理）。
